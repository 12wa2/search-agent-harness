# Evaluation

> 本页只报告仓库内的合成基准，不混用非公开数据或公司指标。所有候选人与查询均为虚构。离线脚本化实验可确定性复现；真实 LLM 实验受模型版本、服务实现和生成随机性影响，不保证每次运行得到完全相同的数值。

## 运行实验

```bash
pip install -e ".[dev]"

# 16 人演示语料：效果 / 成本
search-agent eval --markdown

# 120 人种子化语料：oracle 真值 + 单开关消融
search-agent eval --generated 120 --seed 7 --markdown
search-agent eval --generated 120 --seed 7 --ablate --markdown

# CI 门禁：与已提交基线比较，回归时以非零状态退出
search-agent eval --generated 120 --seed 7 --ablate --baseline docs/eval_baseline.json
```

## 1. 离线成本与候选池

**设置**：16 个演示候选人、3 个查询、脚本化 LLM。该表回答“多花多少钱、候选池铺多宽”，不代表最终列表质量。Q1/Q2 走 Agent，Q3 走直连搜索，因此这是混合了两种路由的“Agent 组”，不是纯完整循环。

| 指标（3 个查询合计） | 单趟基线 | Agent 组 | 变化 |
|---|---:|---:|---:|
| 判定候选（进入 judge 的池子） | 30 人 | 32 人 | +2（+7%） |
| 平均召回完成度 | 0.50 | 0.60 | +0.10 |
| LLM 调用次数 | 6 次 | 11 次 | ×1.8 |
| token 消耗（估算） | ≈12.9k | ≈31.4k | ×2.4 |
| 累计耗时 | 7.1 ms | 14.1 ms | ×2.0 |

> 注意：Agent 组包含 Q3 的 `direct_search`。直连路径的“召回完成度”是 `最终返回数 / topK`，不是 `judged / target`；因此 0.60 不是纯反思循环的平均值，不能与 Oracle/消融表直接横比。

## 2. Oracle 基准：探索层与交付层

**设置**：120 个种子化候选人、6 个查询、交付 top-10。真值来自语料生成器，而不是 Agent 自评。默认 `target_qualified=20`；Agent 可能达到目标或无进展而提前结束，因此这里记录的是自适应 Agent 组，不保证完整八阶段执行。

生成器会让一部分候选人只用项目语言表达能力，例如写“订单交易链路 / 洪峰压测”而不写“高并发”。当前词法打分仍可能因共享语素而部分命中，因此这不是一个“完全不可见”的语义盲区，而是一个被量化过的实现天花板。

| 指标（6 个查询 · micro） | 单趟基线 | Agent 组 |
|---|---:|---:|
| 池召回（探索层：看到过） | 0.70 | 0.76 |
| 召回（交付 top-10：交付到手） | 0.32 | 0.30 |
| 精确率（交付列表） | 0.35 | 0.33 |
| 关键词可见召回 | 0.19 | 0.12 |
| 仅语义可见召回 | 0.36 | 0.36 |
| 仅 Agent 组发现 | — | 平均每条查询多发现 9.0 人，其中合格 0.7 人（7.4%） |

### 怎么读“池召回 → 交付召回”的落差

- 池召回衡量探索：Agent 组把 0.70 抬到 0.76，说明反思确实在扩大搜索范围。
- 交付召回衡量排序：交付 top-10 从 0.32 变成 0.30，说明新增候选没有稳定排进前 10。
- 把交付深度放到 `--top-k 30` 后，Agent 组交付召回升到 0.62；同深度基线为 0.67。损失发生在打分与排序，而不是“完全没有找到人”。
- 当前重排仍是粗粒度词法命中：每个能力只记 0/1，并列时按 `docId` 排序，难以区分“证据充分”和“偶然共享语素”。

## 3. 消融：每个机制值多少钱

同一语料、同一 seed，每一行只关闭一个结构开关。为避免首轮就达标导致差异不可见，消融会把目标合格数抬到语料规模（`target_qualified=120`），强制循环真正迭代。本次运行所有行均为 `degraded=0`。

| 配置 | 池召回（探索层） | 召回（交付 top-10） | 精确率 | 关键词可见 | 仅语义可见 | 仅该行发现（合格） | LLM 调用 | tokens |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 完整循环（强制迭代） | 0.79 | 0.47 | 0.52 | 0.62 | 0.42 | 61 人（6 合格） | 31 | ≈106.3k |
| 去掉收敛再搜 | 0.76 | 0.30（-0.17） | 0.33 | 0.12 | 0.36 | 54 人（4 合格） | 29 | ≈104.1k |
| 去掉签名防重 | 0.79 | 0.47（+0.00） | 0.52 | 0.62 | 0.42 | 61 人（6 合格） | 32 | ≈113.1k |
| 只跑一轮（无 reflect / revise） | 0.76 | 0.30（-0.17） | 0.33 | 0.12 | 0.36 | 54 人（4 合格） | 23 | ≈90.4k |
| 每轮只规划 1 条路径 | 0.79 | 0.47（+0.00） | 0.52 | 0.62 | 0.42 | 61 人（6 合格） | 31 | ≈106.3k |
| 单趟基线 | 0.70 | 0.32（-0.15） | 0.35 | 0.19 | 0.36 | — | 12 | ≈47.9k |

### 结论

- **反思 + 收敛再搜买的是交付**：关掉任意一个，池召回约 0.76，交付召回从 0.47 降到 0.30。
- **当前运行没有显示出多路径收益**：`每轮只规划 1 条路径` 与完整循环同为 `0.79 / 0.47 / 0.52`；旧版本的 `0.76 → 0.70` 结论不再适用于当前代码。要证明多路径价值，需要先确认规划器确实生成互补路径，或使用更复杂的查询集。
- **签名防重是廉价保险**：关掉后质量不变，但 LLM 调用从 31 增到 32、tokens 从约 106.3k 增到 113.1k（约 +6.4%）。
- **下一步应优先修重排**，而不是继续增加路径数。`dense_vector` + RRF 通道已就位，替换 `tools/embedding.py` 的 `embed_text` 即可接入真实 embedding。

### CI 门禁

`docs/eval_baseline.json` 是已提交基线。本次 `--baseline` 校验通过；质量指标与当前运行基本一致，但 tokens/耗时来自历史快照，不作为逐毫秒复现值，且 timing 不参与门禁。CI 的 `eval-gate` 作业在每次 push 时比较池召回、交付召回、精确率、成本和降级次数；超出允许漂移会直接失败。

## 4. 真实 LLM + Hybrid V2 的 A/B 复核

> 下表是旧版轻量字段语料的已记录结果，保留作历史对照。仓库当前使用的复现基准已切换为 V2 原生字段语料 `examples/bench_v2_100`；使用新语料重跑后，应更新本节指标。

**历史设置**：旧版 100 个轻量字段候选人、10 条复杂查询、Elasticsearch 索引 `search-agent-hybrid-v2-bench100`、`qwen3.8-flash`、交付 top-5。基线为 `understand → 单路径 → judge → finalize`；实验组为 Agent 反思链路。两条链路共享语料、模型、检索工具和标注集；基线并非零 LLM，唯一结构变量是反思循环。

| 指标 | 单趟基线 | Agent 反思循环 | 变化 |
|---|---:|---:|---:|
| 平均 recall@5 | 0.392 | 0.473 | +0.081（bootstrap 95% CI -0.031 ~ +0.201） |
| 平均池召回 | 0.735 | 0.937 | +0.202（CI +0.065 ~ +0.351） |
| 平均 precision@5 | 0.740 | 0.840 | +0.100（描述性） |
| Agent 独有交付候选人 | — | 24 人 | — |
| 其中相关 | — | 17 人（1.7 / query） | — |
| 新增候选相关率 | — | 0.708 | — |
| LLM 调用 | 20 | 59 | ×3.0 |
| tokens | 148,428 | 446,704 | ×3.0 |
| p50 延迟 | 50.7 s | 139.9 s | ×2.8 |
| p95 延迟 | 57.0 s | 185.3 s | ×3.3 |
| 降级次数 | 0 | 2 | — |

### 结果边界

- 池召回提升明显，且配对 bootstrap 区间不包含 0。
- top-5 召回提升的平均区间跨过 0；这 10 条合成查询不足以证明稳定的平均交付提升。
- 精确率没有因扩大召回而下降；24 个 Agent 独有交付候选人中 17 个相关（0.708）。Precision@5 的提升没有配对 CI，只作描述性报告。
- 成本约为 3 倍；两条查询触发 `budget_exceeded`。
- 并非每条查询都提升：`microservice_backend` 的 recall@5 从 0.333 降到 0.133；`data_realtime` 扩大了池但没有提升交付。
- 下一轮应优先修 judge / rerank 精度、收敛再搜的预算分配，以及落后查询族的失败分析。

## 5. 解释边界

- 语料和标签公开、合成；标签来自生成器 oracle，不是人工标注；绝对数值不能与公司数据或生产 A/B 直接比较。
- 真实模型实验只覆盖一个模型配置，每个查询一次观测；这里的 bootstrap 区间是描述性的，不是显著性检验。
- A/B 报告记录的是服务入口结果，未逐条记录实际执行阶段；不能据此断言每条 Query 都执行了全部八阶段。
- 离线脚本化 LLM 是规则替身，用于验证链路、预算和回归，不代表真实模型能力。
- 本页不报告无法在仓库内复现的非公开指标。
