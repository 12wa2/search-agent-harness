# 技术规划

> 本页记录当前公开实现中已识别的工程瓶颈、待验证假设、实验设计和预期收益。它是技术判断，
> 不是已交付能力、功能承诺或生产 SLA。未通过公开评测的优化不会写入 README 的结果摘要，
> 也不会在 CHANGELOG 中标记为已实现。
>
> 当前基线为 100 个合成候选人、10 条复杂 Query、top-5，详见[评测报告](EVALUATION.md)。
> 这些结果用于分析工程机制，不能直接外推到真实招聘语料或生产流量。
>
> 候选人排序与综合优先级的专项设计见[排序设计草案](TO_PLAN.md)。

## 优先级

| 优先级 | 方向 | 当前证据 | 本轮要回答的问题 |
|---|---|---|---|
| P1 | 真实 Embedding 与语义召回 | 公开评测默认使用确定性 hash embedder；外部 embedding 已接入，但尚未形成可比较的正式基线 | 语义向量是否能在词法匹配之外召回同义表达与可迁移经验？ |
| P2 | Judge / Rerank 的证据粒度 | 池召回为 `0.875`，Recall@5 为 `0.425`；部分查询存在“探索有货、排序丢货” | 让判断和重排使用逐条件证据，能否减少进入候选池但未进入交付名单的相关候选人？ |
| P3 | 按查询族分配预算 | Agent 链路约为基线的 `3.25x` LLM 调用、`3.64x` tokens、`3.40x` p50 延迟；收益并不均匀 | 能否在不降低 Recall@5 的前提下，把预算集中到真正需要反思的查询族？ |

## P1：把真实 Embedding 纳入可复现评测

**现状**

Hybrid V2 支持 `hash` 与 OpenAI-compatible embedding；公开演示和仓库评测默认使用
`hash`，以保证零 Key、确定性复现。该 embedder 是词法哈希，不提供训练后的语义表示，
因此当前公开指标不能回答“语义召回是否有效”。

**假设**

真实 embedding 可以补足 BM25 与 hash 向量对同义表达、跨岗位经验和抽象能力的召回缺口。
例如“支付清算”与“交易结算”、“高并发系统”与“稳定性治理”之间的关联，不应只依赖字面重合。

**实验设计**

1. 固定候选人、Query、人工/自动标签、ES mapping、模型别名和重排策略，只替换 embedding
   provider、模型与维度；索引重建后确认 query/document 维度一致。
2. 分别记录 BM25、kNN 与融合后的候选池贡献，避免只比较最终 Recall 而无法解释收益来源。
3. 对比池召回、Recall@5、Precision@5、逐 Query 相关候选人增量，以及索引时间、查询延迟和
   embedding 成本。
4. 先在当前 10 条 Query 上做描述性分析；在扩大查询族并重复观测前，不声称统计显著性。

**验收标准**

- 至少一个核心指标出现可复现提升，且 Precision@5 不出现无法解释的明显下降；
- 能指出提升来自哪些同义表达或可迁移能力，而不只是向量维度变化；
- 公开评测保留相同数据与模型配置，并报告成本、延迟和失败案例。

**风险**

- 更换 embedding 需要重建索引，历史实验不能直接混合比较；
- 托管模型存在版本漂移、费用和网络依赖；
- 语义召回可能扩大候选池，但把排序压力转移到 Judge / Rerank。

## P2：提升 Judge / Rerank 的证据粒度

**现状**

当前评测中池召回为 `0.875`，Recall@5 为 `0.425`，说明仍有相关候选人进入候选池后没有
进入最终前五。`stability_capacity`、`microservice_backend` 等查询族也出现了 Recall@5
回退，不能只用“候选池不够大”解释。

**假设**

把岗位要求拆成可核验的条件，并为每个条件保留候选人字段、来源片段和硬约束状态，可以让
Judge 判断与 Rerank 排序共享同一份证据单元。相比把整份简历或纯摘要交给模型，这种方式
更容易保留关键上下文，也能减少无关 token。

**实验设计**

1. 为每条要求生成 `must / nice-to-have / exclude` 结构化证据，记录命中的字段、片段与
   证据类型；完整简历不进入提示词，只使用有长度上限的证据片段。
2. 设计两套可比较的排序信号：现有本地 reranker，以及“逐条件证据 + 硬约束优先级”的
   `evidence_v2`；两者使用相同候选池和标签。
3. 增加 `NDCG@5`、逐 Query 错排案例、证据覆盖率与 judge 一致性统计，避免只看 Recall@5。
4. 对失败 Query 做人工回读，区分“证据未召回”“Judge 判断错误”和“Rerank 排序错误”。

**验收标准**

- 在多数查询族上提高 Precision@5 或 NDCG@5，且 Recall@5 不出现系统性回退；
- 每个交付候选人都能追溯到具体条件与来源字段；
- Token 和延迟增长保持在现有预算以内；若无净收益，保留当前策略并记录负结果。

**风险**

- 更细的提示词会增加上下文长度和调用成本；
- 自动生成证据可能放大标签偏差，需要抽样人工复核；
- 证据片段必须视为不可信数据，继续遵守现有的提示词注入边界。

## P3：按查询族分配收敛与再搜预算

**现状**

完整反思链路相对单趟基线增加约 `3.25x` LLM 调用、`3.64x` tokens 和 `3.40x` p50 延迟，
但并非每条 Query 都提升；部分结构化查询不需要多轮探索。当前统一预算对简单和不均衡查询族
都会产生不必要的成本。

**假设**

查询条件可以从少量可解释特征中归类，例如硬条件数量、是否存在抽象能力、开放式偏好、
负向约束和会话承接。为不同查询族配置不同的轮数、路径数与再搜预算，可以在保持质量的同时
降低平均成本。

**实验设计**

1. 先用确定性规则提取特征，评估离线策略表；只有在规则无法区分时才考虑一次轻量分类调用。
2. 对每组 Query 固定候选池和 top-5，比较 `reduced`、`standard` 与按族预算策略的
   Recall@5、tokens、LLM 调用、p50/p95 和预算触发率。
3. 报告“每 1k tokens 的 Recall@5”，并单独检查预算收紧后是否漏掉硬条件候选人。
4. 扩大 Query 数量并保留至少一组未参与调参的查询作为留出集，避免针对当前 10 条 Query 过拟合。

**验收标准**

- 相同或更好的 Recall@5 下显著降低 tokens 或 p95 延迟；或成本不变但稳定提升质量；
- 预算触发行为可解释，不能以牺牲硬约束正确性换取成本指标；
- 结论必须在留出查询族上复现，否则只作为实验观察。

**风险**

- 当前 10 条查询不足以稳定估计查询族差异；
- 分类器本身会增加调用与延迟，必须计入成本；
- 预算调整不能绕过既有的状态机安全上限、取消边界和降级矩阵。

## 共同验收规则

- 每次实验只改变一个结构变量，固定模型别名、语料、标签、ES 配置和排序口径。
- 同时报告质量、成本、延迟和逐 Query 失败案例；bootstrap 区间只作为描述性信息，不替代
  显著性检验。
- 先补测试与可复现脚本，再更新 README 指标；负结果同样保留在评测文档中。
- 不引入真实简历、企业数据或凭据。任何外部数据接入都必须在获得授权和完成脱敏后进行。

## 不在这份规划中

- 生产级高可用、多租户隔离和大规模索引运维；
- 用人工标注替代当前合成标签的完整研究项目；
- 为单次演示临时调参或挑选有利 Query；
- 将尚未验证的优化写成已实现能力。
