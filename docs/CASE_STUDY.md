# 案例研究：一条 Query 的完整走查

一条真实（离线可复现）的查询，从自然语言到交付列表的八个阶段，逐阶段贴真实中间产物——
数字全部来自 `search-agent demo` 的输出，没有任何修饰。它同时也是**面试讲解的提词器**：
读到哪一段，就讲哪一段。

```bash
search-agent demo "找有 3 年以上经验、做过高并发系统的后端工程师，最好来自大厂" --top-k 5
```

数据来源：仓库自带的 16 个虚构候选人（`c001`–`c016`）+ 脚本化 LLM（确定性规则替身），
零 API key、可复现。

## 端到端时间线

```text
  [1/8 understand] 岗位=后端工程师  必须能力=['高并发系统设计', '服务端开发']  硬条件=1 条
  [2/8 plan] 生成 2 条搜索路径 → p1: 硬条件精准匹配 | p2: 放宽硬条件的语义拓宽路径
  [3/8 execute] 并行执行 2 条路径，召回 30 人次（p1:rich, p2:rich）
  [4/8 judge] 能力级判断完成，累计合格候选人 16
  [5/8 evaluate] → reflect
  [6/8 reflect] 共性=['普遍命中：服务端开发', '普遍命中：高并发系统设计']  缺口=['高并发系统设计']  新增软信号=2
  [7/8 revise] 画像软信号=6  收敛=False  迭代=1
  [8/8 finalize] 最终 5 人（收敛再搜 14 人次）
```

## 逐阶段拆解

### 1. understand：把一句话变成可执行的画像

- 岗位：**后端工程师**；难度 mid。
- 必须能力 2 条，每条带证据词（`evidence_hints`）：
  - `高并发系统设计` ← 高并发 / QPS / 流量 / 性能优化 / 大促
  - `服务端开发` ← 后端 / 服务端 / Java / Go / Python
- 硬条件 1 条：`work_years >= 3`（required）。
- 人才画像：来源假设 `s1 = 一线互联网大厂`（transferable，对应查询里的「最好来自大厂」）+
  2 条软信号（各 weight 1.5）。

> 讲解点：证据词不是装饰——judge 阶段用它做 grounding（候选人简历里找不到证据的能力会被降级），
> 所以「能力」必须可被验证，而不是一句形容词。

### 2. plan：两条意图不同的路径 + 签名

| 路径 | 意图 | 硬条件 | 语义条件 | 签名（前 8 位） |
|---|---|---|---|---|
| `p1` | 硬条件精准匹配 | `work_years >= 3` | 高并发系统设计 / 服务端开发 | `6cb6ee82` |
| `p2` | 放宽硬条件的语义拓宽 | `work_years >= 0` | 同上 | `95148761` |

> 讲解点：每条路径的 `signature` 是意图（IR）的指纹，进入 `tried_signatures`；
> 反思后若想再走同一个意图，会在 revise 阶段被签名防重挡掉——本案例最后 `tried_signatures`
> 里就是这 2 条。

### 3. execute：并行执行，池子铺开

两条路径并行（线程池），各召回 16 人（整个语料），两条都是 `quality=rich`，合计 **30 人次**。
每路径召回池大小为 `max(top_k*3, 30)`，judge 全量池、最终只交付 `top_k`。

### 4. judge：能力级判断 + 证据 grounding

16 人全部进入 judge（累计判定 16），每条判断带 `matched_abilities` / `missing_abilities` /
`source_path_ids`。指标：能力覆盖 0.594 · 硬条件命中率 1.0 · 真正命中 13 人。

> 讲解点：judge 的输出不是「分数」，而是「哪几个能力被证据支持」，这样最终解释能落到
> 「为什么是这个人」（交付列表里每个人都带 `matchedAbilities` + `pathRationale`）。

### 5. evaluate：16 / 目标 20 → 还不够，继续

未达标（16 < 20），进入 reflect。

### 6. reflect：从结果反推共性 / 缺口 / 新信号

```json
{
  "common_traits": ["普遍命中：服务端开发", "普遍命中：高并发系统设计"],
  "gaps": ["高并发系统设计"],
  "inferred_soft_signals": [
    {"text": "服务端开发", "fields": ["work_vector", "project_vector"], "weight": 1.2},
    {"text": "高并发系统设计", "fields": ["work_vector", "project_vector"], "weight": 1.2}
  ],
  "new_source_hints": [],
  "path_actions": []
}
```

### 7. revise：没有可执行的改进动作 → 收束

`path_actions` 为空、`new_source_hints` 为空 → revise 不新建路径（画像连软信号都没变，
`profile_converged=False` 但无改进空间），直接进入 finalize。

> 讲解点：这是「知道什么时候停」。循环没有为了跑满 3 轮而硬凑一轮——
> 终止条件在 `core/budget.py::should_finalize`，`core/signature.py` 保证不会重复搜同一意图。

### 8. finalize：收敛再搜 + 合并重排

- 收敛再搜（用反思后的画像做一次确定性搜索）：召回 14 人次，**新增 0**（都已判过）。
- 交付 = 合并池 + 全局重排（`rerankUsed=true`）→ top-5：

| # | 姓名 | 年限 | 分数 | 命中能力 | 来源路径 |
|---|---|---|---|---|---|
| 1 | 赵敏 | 4 | 3.01 | 高并发系统设计、服务端开发 | 硬条件精准匹配 |
| 2 | 李娜 | 6.5 | 2.75 | 同左 | 硬条件精准匹配 |
| 3 | 张伟 | 8 | 2.59 | 同左 | 硬条件精准匹配 |
| 4 | 朱琳 | 7.5 | 2.59 | 同左 | 硬条件精准匹配 |
| 5 | 许诺 | 6 | 2.40 | 同左 | 硬条件精准匹配 |

运行指标：LLM 5 次（understand 1 + plan 1 + judge 2 + reflect 1）· token ≈12.8k（估算）·
迭代 1 轮 · 耗时 6 ms · 降级=无 · 预算余量充足（上限 40 次调用 / 3 轮 / 12 秒）。

## 这个案例说明了什么（也说明没说明什么）

1. **循环的第一价值是「知道何时停」**：reflect 发现没有改进空间就收束，1 轮结束。
   在更难的查询上（oracle 基准里），同一套逻辑会多跑轮次并用「来源假设」换召回方向。
2. **收敛再搜不是银弹**：本例新增 0 人——池子只有 16 人时它只是确认「没漏」。
   它的价值在候选池远大于 `top_k` 的真实库里（代价是一次后端查询 + 一次重排，不带 LLM judge）。
3. **多路径在小而同质的池子里会重叠**：p1 / p2 只有年限阈值之差，召回的是同一批人。
   消融表里是同一现象：多路径买的是探索宽度（池召回 0.70 → 0.76），但在词法打分下
   转化不成交付（0.42 → 0.41）——收益要等真实 embedding 的语义召回。
4. **「合格 16」是代理指标**：由 judge 判定（有 grounding 约束），不是人工真值；
   真值口径见 `search-agent eval --generated`（oracle），人工反馈闭环在 Roadmap。

## 面试怎么讲（60 秒口播稿）

> 这是一条「3 年经验 + 高并发 + 大厂偏好」的后端岗查询。系统先把它拆成两条必须能力和一条硬条件，
> 然后规划两条意图不同的路径——精准路径和放宽年限的语义路径——并行执行，召回 30 人次。
> judge 逐人做能力级判断，并且要求候选人简历里有证据，最后判定 16 人达标。
> 但没到目标数，所以进入反思：它发现大家都命中同样两个能力、缺口也在同一个能力上，
> 输出不了新的搜索方向，于是 revise 没有可执行动作，系统直接收束到 finalize——
> 用反思后的画像做一次收敛搜索，再做全局重排交付 top-5。
> 全程 5 次 LLM 调用、约 1.3 万 token、6 毫秒，无降级。
> 我特意保留了「收敛再搜新增 0 人」这个结果：它说明这套机制不是银弹，
> 所以我把每个机制的收益用消融表逐项量过，负收益的那条也写在 README 里。

## 追问预案

| 追问 | 回答要点 |
|---|---|
| 两条路径召回一样，多路径是不是没用？ | 本例池子只有 16 人且两路径只差年限阈值；真实库里语义路径负责召回关键词搜不到的人（oracle 基准单独统计「仅语义可见」）。消融表里多路径只扩大探索池（0.70 → 0.76）、不抬交付且成本 ≈2×——收益前提是真实 embedding 打分。 |
| 收敛再搜 0 新增，为什么还要保留？ | 它成本低（一次后端查询 + 重排，新增候选才走 judge），作用是确认覆盖、并在大池子里带回漏网的人；在 `--generated` 基准上它贡献 +0.11 交付召回（消融表：关掉后 0.41 → 0.30，池召回不变——价值在交付层而不在探索层）。 |
| 为什么 1 轮就停了？ | `should_finalize`：reflect 没有可执行改进动作 → 「没有改进空间」终止，不为跑满轮次而硬凑；硬约束在预算（轮数 / LLM 调用 / token / 时间）。 |
| 「合格 16」谁判的？可信吗？ | LLM judge + 证据 grounding（简历里找不到证据的能力降级），属代理指标；真值看 oracle 基准，人工反馈闭环在 Roadmap。 |
| 为什么只有 5 次 LLM 调用？ | understand 1 + plan 1 + judge 2（每条路径一次）+ reflect 1；finalize 的收敛再搜不调 LLM（只对新增候选 judge，本例 0 新增）。 |

## 100 人真实模型复核：一个成功案例与一个回退案例

上面的 16 人案例用于解释阶段和确定性行为；正式展示还需回答「换到真实 LLM、真实 ES 和更大语料后
是否仍成立」。仓库中的 `examples/real_ab_experiment.py` 因此固定同一 Qwen 网关、Hybrid V2 索引、
`top-k=5` 和同一套 `synthetic_oracle` 标签，只切换 `reflect + revise`。

**成功案例 `backend_concurrency`**：基线交付 5 人、相关 0 人；Agent 交付 5 人、相关 4 人，
池召回从 `0.250` 升到 `0.875`，并带回 `g015`、`g029`、`g085`、`g099` 四个基线没有交付的相关候选人。
这条 query 能说明反思的价值：第一次搜索没有找到足够的“高并发 + 后端”证据时，系统会换搜索方向，
而不是在原查询上反复调参。

**回退案例 `microservice_backend`**：基线 recall@5 为 `0.333`，Agent 反而降到 `0.133`；另有
`backend_concurrency`、`payment_distributed_tx` 在预算上限触发 `budget_exceeded`。这说明“探索得更宽”
不等于“最终排序更准”：候选进入池以后，judge / rerank 和预算分配仍可能把正确的人挤下去。
面试时不应隐藏这条回退；它恰好能引出下一阶段优化方向。

完整 10 条 query 的逐条结果、成本、bootstrap 区间与边界见
`docs/real_llm_ab_results_100.md`。
