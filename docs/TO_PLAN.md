# 候选人排序与综合优先级：未来设计

> 状态：设计草案，尚未实现。本文记录未来可能采用的产品与技术方案，不代表当前已交付能力。
>
> 最后更新：2026-10-31

## 1. 当前基线

当前产品已经区分两种检索路径：

- **Agent 路径**：`finalize` 生成综合顺位，前端展示 `综合顺位 #N`；不在候选人卡片上展示 reranker 分数。
- **直连路径**：`direct_search` 按 Hybrid V2 reranker 顺序返回，前端展示相关度分数。

Agent 路径的综合顺位由 `_selection_key()` 和硬条件软门控共同决定。默认 `current` 策略下依次比较：

1. must 能力命中数（降序）
2. must 能力缺口（升序）
3. 显式硬条件违规数（升序）
4. 简历证据命中数（降序）
5. 简历证据缺口（升序）
6. 是否已经过 Judge 判定（已判定优先）
7. 总能力命中数（降序）
8. reranker score（降序）
9. `doc_id`（稳定排序）

排序后再执行硬条件软门控：

```text
硬条件满足/不适用 → 硬条件待核实 → 硬条件违规
```

这里的综合顺位是**分层排序结果**，不是加权总分。当前 `路径证据 N` 主要用于展示来源数量，在默认 `current` 策略下不是直接排序键；路径一致性只在 `judge_gate` / `judge_gate_v2` 策略中参与排序。

当前 `_candidate_text()` 的简历证据主要来自摘要、技能、职位/公司、期望岗位和证书，尚未直接解析项目描述。这一点是后续提升证据粒度的重点。

## 2. 为什么不直接增加综合分

把综合顺位压成一个数字，至少需要解决以下问题：

- must 覆盖、证据覆盖、硬条件和相关度的量纲不同；
- 硬条件不适合用高相关度补偿，否则会破坏准入语义；
- 权重变化会改变排序，需要业务依据和评测支撑；
- 单一分数容易被误读为概率、通过率或跨查询可比较的质量分；
- 前端临时拼分会破坏“分数与真实顺位一致”的承诺。

因此，**默认保留综合顺位，不为了显示数字而引入未校准的综合分**。

## 3. 目标

- 默认继续使用综合顺位，硬条件和 must 能力优先于相关度。
- 相关度分数在 Agent 主视图中不展示，仅保留在内部 Trace 或展开详情中用于排查。
- 如果未来增加数字分，必须由后端计算，并与最终展示顺位保持一致。
- 直连路径继续展示 reranker 相关度，因为该路径确实按相关度排序。
- 任何新排序视图都必须基于完整候选人池排序后再分页，不能只重排当前页。

## 4. 未来设计

### 4.1 后端返回排序元数据

建议后端新增一个独立的 ranking 元数据对象，不覆盖现有 `score` 字段：

```json
{
  "rank": 1,
  "tier": "T0",
  "components": {
    "mustMatched": 3,
    "mustTotal": 4,
    "evidenceMatched": 2,
    "evidenceTotal": 4,
    "hardConditionStatus": "satisfied",
    "pathCount": 2
  },
  "rerankScore": 0.62
}
```

约定：

- `rank` 来自 `final_items` 的最终位置，是展示顺位的唯一来源；
- `rerankScore` 保留为内部参考分，Agent 卡片默认不展示；
- `components` 用于解释排序原因和展开详情；
- 不把 `rerankScore` 改名成“匹配率”或“通过率”。

### 4.2 可选的综合优先级分

如果后续确实需要一个数字分，建议采用“资格层级 + 层内分数”的两层结构：

```text
第一层：资格层级
  T0：硬条件满足 + must 全覆盖 + 证据完整
  T1：硬条件满足 + must 全覆盖 + 证据不足
  T2：硬条件满足 + 缺少一个 must 能力
  T3：硬条件待核实/违规/未判定

第二层：同层内综合优先级分
  must 覆盖比例
  + 简历证据覆盖比例
  + 路径一致性
```

硬条件作为门槛，不进入加权平均；相关度不进入 Agent 主展示分，必要时只作为层内最后的 tie-breaker。

如果无法完成权重校准和回归测试，则不实现这个分，继续使用 `综合顺位 #N`。

### 4.3 双排序视图

未来可以提供两个排序视图，但必须共享同一候选人池：

| 视图 | 排序依据 | 适用场景 |
|---|---|---|
| 综合顺位（默认） | 硬条件、must 能力、证据、路径一致性 | 交付、入围、HR 决策 |
| 相关度 | reranker score | 探索、验证搜索词、排查漏人 |

接口草案：

```text
GET /sessions/{query_token}?sort=composite|relevance
```

实现约束：

- 后端对完整候选人池排序后再切片分页；
- 切换视图重置到第一页；
- Agent 的相关度视图必须提示“硬条件可能未满足”；
- 直连路径始终使用 reranker 顺序，不需要再提供综合顺位视图。

### 4.4 提升证据粒度

当前排序的“简历证据”还没有直接解析项目经历。未来建议补充：

1. 将 `projectExperiences` 的项目名称和描述纳入证据文本；
2. 为每个 must 能力保留命中的字段、片段和来源路径；
3. 区分“简历明确写出的证据”和“从项目描述推断的可迁移能力”；
4. 在候选人详情中展示 `证据命中`、`证据缺口` 和 `未核实项`；
5. 所有解释必须来自真实候选人字段，不允许 LLM 补写项目细节。

### 4.5 排序原因展示

候选人展开后可以展示：

```text
综合顺位 #1
must 能力 3/4
证据覆盖 2/4
硬条件 满足
来源路径 2 条
排序原因：must 能力优先，其次证据覆盖
```

这比一个未校准的 `87 分` 更容易解释，也更能体现 Agent 的判断过程。

## 5. 验收标准

- Agent 默认视图不展示 reranker 相关度数值；
- `综合顺位 #N` 与后端 `final_items` 顺序完全一致；
- 硬条件违规候选人不能因为相关度高而排到满足者前面；
- 综合优先级分（如果实现）在同一资格层级内与展示顺序一致；
- 双视图排序必须覆盖完整候选人池，翻页顺序稳定；
- 相关度视图明确标注其不代表硬条件合格；
- 增加至少一组回归测试，覆盖 Agent / 直连两条路径和分页切换。

## 6. 实施顺序

1. **P0**：保持当前综合顺位、硬条件软门控和 `综合顺位 #N` 展示；
2. **P1**：补项目经历证据和路径级证据解释；
3. **P2**：评估双排序视图，先做后端完整池排序与分页；
4. **P3**：只有在权重、校准和评测通过后，再引入后端综合优先级分；
5. **P4**：再考虑入围名单持久化和导出等业务闭环能力。

## 7. 不在本次设计中

- 用前端现有字段临时拼一个综合分；
- 用高相关度抵消硬条件违规；
- 把综合分宣称为概率、通过率或跨查询可比较的质量分；
- 为了展示分数而改变当前硬条件交付语义；
- 把尚未验证的排序策略写成已实现能力。
